1단계데이터 수집

사람이 눈으로 볼 수 없는 양의 데이터를 프로그램이 정해진 주기마다 자동으로 모읍니다. 이 단계 자체는 판단이 없는 반복 작업(매크로)이고, 여기서 중요한 건 빠짐없이, 그리고 원본 그대로 모으는 것입니다.

수집하는 데이터와 규모

데이터내용과 규모주 용도
국내 주식 일봉수백 종목 × 수년치의 하루 단위 시가·고가·저가·종가·거래량전략 검증(백테스트), 매일의 판단 재료
국내 주식 분봉1분 단위 가격·거래량. 약 400종목 × 1년 = 2천만 개가 넘는 봉장중 움직임 분석, 초단타 전략 검증, 리플레이 시뮬레이터
기업 공시의무공시 수만 건 — 자사주 취득·소각, 신탁 계약·해지, 최대주주 변동, 실적, 증자 등. 제목만이 아니라 원문에서 금액·방식까지 추출이벤트 기반 전략의 출발점
투자자별 수급외국인·기관 등 주체별 순매수 동향수급 신호 검증, 판단 보조
미국 지수·원자재나스닥·S&P·금 등의 수십 년치(약 27년) 가격 이력자산배분(추세추종) 전략, 시장 국면 판단
미국 내부자 거래임원·대주주가 자사 주식을 샀다는 공적 신고 데이터내부자 매수 신호 전략 검증
뉴스·감성종목·시장 관련 기사 크롤링 + 긍정/부정 자동 분류판단 보조, 종목 간 관계 파악
암호화폐 시세거래소 API 기반 코인 수십 종의 시세 (동일 파이프라인을 코인 시장에도 운용)코인 전략 검증·운용

수집기가 실제로 하는 일

  • 속도 제한 준수 — 거래소·증권사 API는 초당 호출 횟수 제한이 있어, 수집기는 호출 간격을 두고 순차 진행합니다. 분봉 1년치 400종목을 새로 받는 데 반나절 이상 걸리며, 이걸 감수하고 전부 받습니다.
  • 증분 수집 — 매번 처음부터 받지 않고, 이미 있는 데이터 이후 구간만 받습니다.
  • 실패 추적과 재시도 — 실패한 항목(예: 상장폐지 종목)을 따로 세고, 재시도 가능한 것만 다시 받습니다. 데이터에 구멍이 나면 뒤의 모든 단계가 오염되기 때문입니다.
  • 원본 보존 — 받은 그대로를 저장하고 가공은 다음 단계에서 합니다. 가공 로직에 버그가 있어도 원본으로 되돌아갈 수 있습니다.

2단계데이터 처리

  • 정리 — 시간순 정렬, 중복 제거, 거래정지·상장폐지 구간 표시. 살아남은 종목만 남기면 "생존 편향"이 생기므로 죽은 종목도 데이터에 그대로 둡니다 (이걸 빼면 과거 수익률이 실제보다 좋아 보입니다).
  • 지표 계산 — 이동평균(추세), 변동성(그 종목이 평소 얼마나 움직이는지), 거래량 배율(평소 대비 몇 배 터졌는지), 가격 위치(52주 범위에서 바닥권인지) 같은 파생 수치를 만들어 붙입니다.
  • 공시의 구조화 — 공시 원문(문서)에서 "어느 회사가, 언제, 무엇을, 얼마나, 어떤 방식으로"를 뽑아 표 형태로 만듭니다. 이후 전략은 이 구조화된 이벤트를 재료로 씁니다.
  • 시장 단면 계산 — 특정 시각에 전체 종목 중 몇 %가 하락 중인지 같은 "시장 전체 상태"를 만들어 둡니다.
대원칙 — 미래 정보 차단 (look-ahead 방지)
과거 데이터로 전략을 검증할 때 "그 시점엔 알 수 없었던 정보"가 한 조각이라도 섞이면, 실제로는 손해인 전략이 서류상 큰 이익처럼 보입니다. 실제로 겪은 오염 사례:
  • 공시가 장 마감 후에 나왔는데 당일 가격으로 산 것처럼 계산 → 다음 거래일 진입으로 강제 수정
  • "그 날 가장 많이 떨어진 종목을 산다"는 규칙 — 실제로는 장이 끝나야 그 날 최대 하락 종목을 알 수 있는데 장중에 안 것처럼 계산 → 폐기
  • 여러 종목의 동시 급락(군집)을 확인하고 진입하는 전략 — 군집이 완성되기 전 가격으로 진입한 것으로 계산돼 겉보기 수익률이 몇 배로 부풀려짐 → 발견 즉시 통째로 폐기
모든 검증 코드는 "판단 시점 이전 정보만 사용"을 구조적으로 강제하고, 위반이 발견되면 성과가 아무리 좋아도 결과 전체를 버립니다.

3단계전략 연구와 검증

시스템의 심장입니다. "어떤 조건에서 사고팔면 이득인가"라는 가설을 세우고, 과거 데이터로 실험하고, 대부분을 탈락시킵니다.

검증 관문

  1. 비용 반영 — 수수료(약 0.015%), 매도 시 거래세(약 0.15%), 체결 밀림(슬리피지) 편도 0.2% 수준을 가정해 왕복 약 0.4%를 뺍니다. 비용 반영 전 흑자인 전략의 상당수가 여기서 적자로 바뀝니다.
  2. 기간 분리 — 데이터를 앞/뒤 기간으로 나눠 양쪽 모두에서 성립해야 인정합니다.
  3. 우연 대조 — 같은 조건에서 무작위로 골랐을 때의 성적을 먼저 재고, 전략이 그것을 통계적으로 이겨야 합니다.
  4. 재추출 검증(부트스트랩) — 매매 기록을 무작위로 다시 뽑아 수천 번 재구성했을 때 몇 %가 흑자인지 봅니다. 소수의 대박이 전체를 끌고 가는 착시를 걸러냅니다.
  5. 소수 종목 의존 검사 — 상위 몇 종목을 빼도 성립하는지 확인합니다.
  6. 다중 실험 보정 — 수백 가지 조합을 실험하면 우연히 좋아 보이는 것이 반드시 나오므로, 실험 횟수를 감안해 기준을 높입니다.

관문을 통과해 승인된 전략 (예)

  • 자사주 이벤트 전략 — 회사가 자기 주식을 사겠다고 공시(취득 결정, 신탁 해지)했고 주가가 1년 범위의 바닥권일 때, 공시 다음 날 진입해 정해진 날짜에 청산. 수년치 공시 전수 데이터에서 대조군 대비 초과 수익이 통계적으로 유의미했고 앞/뒤 기간 모두 성립.
  • 지수 추세 자산배분 — 나스닥·S&P·금 ETF를 나눠 들되, 각 자산이 장기 추세선 아래로 내려가면 그 자산만 현금으로 피신. 약 27년 데이터에서 연 수익률을 유지하면서 최대 낙폭을 크게 줄이는 효과가 시대 불문 성립.
  • 코인 급락 매수 — 시장 전체가 약세가 아닐 때의 개별 코인 급락 매수. 동일 검증 절차를 거쳐 소액 운용.

탈락한 전략 (예 — 이것도 자산)

  • 분(分) 단위 초단타 전 계열 — 1분봉 2천만 개로 손규칙 수만 조합, 12가지 이론의 전문가 에이전트, 종목별 기억, 차트 유사도 검색(과거 260만 구간), AI 다중 토론까지 실험. 결론: 거래 비용과 장중 하락 편향을 이길 정보가 1분봉 안에 없음. 서로 다른 5가지 방법이 같은 크기의 손실로 수렴함을 확인하고 계열 폐기.
  • 국내 일봉 가격 신호 계열 — 가격·거래량만으로 종목을 고르는 방식 여러 갈래, 비용 반영 후 장기 우위 없음 → 폐기.
  • 거래량 급증 신호 — 겉보기 성과가 신호의 힘이 아니라 분산 효과의 착시로 판명 → 폐기.

4단계신호 생성

승인된 전략의 조건이 실제 시장에서 발생하는지 상시 감시합니다. 가벼운 규칙이 "볼 가치가 있는 순간"만 걸러내는 단계로, 사람으로 치면 "알림이 떠서 차트를 여는 순간"입니다.

  • 공시 수집기가 새 공시 발견 → 전략 조건(유형·금액·주가 위치)과 대조 → 부합 시 후보 등록
  • 매일 장 마감 후 지수·ETF 추세 위치 재계산 → 추세 이탈/복귀 시 리밸런싱 후보 등록
  • 장중 급락·거래량 폭증 감지 → 해당 전략이 승인돼 있으면 후보 등록

후보는 "즉시 매수"가 아니라 다음 단계의 입력입니다.

5단계에이전트 판단

에이전트입력받는 정보내는 판단
이벤트 분석공시 원문, 같은 유형 공시의 과거 전수 통계, 해당 기업의 과거 이행률"이 공시는 규모·맥락상 과거 통계의 적용 대상이 맞다 / 아니다"
가격·수급가격 위치, 거래량, 추세, 투자자별 수급"진입 조건 부합 / 조건 이탈"
시장 상태시장 전체의 방향·변동성·하락 종목 비율"시장 급락 중 — 신규 진입 보류" 같은 거부권
리스크 관리포트폴리오 구성, 업종 쏠림, 자금 한도"업종 비중 초과 — 수량 축소 또는 반려"
최종 관문위 전원의 의견승인/반려 + 수량·가격·청산 계획이 담긴 주문서

핵심 설계는 합의제와 거부권입니다. 다수가 동의해야 진행하고, 하나라도 강한 반대 사유를 내면 매매하지 않습니다. 반려 사유까지 전부 기록에 남습니다.

AI(대형 언어모델)의 위치 — AI는 계산기가 아니라 "맥락 판단자"입니다. 숫자·통계는 일반 코드가 하고, AI는 공시 원문 해석이나 여러 근거의 종합 같은 정성 판단을 맡습니다. AI의 판단력 자체도 검증 대상입니다 — "AI가 고른 것 vs 고르지 않은 것"의 실제 성과 차이를 측정해, 차이가 없으면 그 역할에서 AI를 뺍니다.

6단계매매 실행

주문의 생애주기

  1. 주문서 생성 (종목·수량·가격·청산 계획 포함)
  2. 실행 전 검증 — 잔고·한도·중복 주문·개장 여부
  3. API 전송 → 체결 확인 (미체결 시 정해진 규칙으로 재시도/취소)
  4. 체결 즉시 기록 저장, 청산 계획(손절선·보유 기한) 등록
  5. 보유 중 상시 감시 — 손절선·기한·청산 신호 발생 시 자동 매도

안전장치

  • 자금 배분(슬롯) — 전체 자금을 여러 칸(예: 12칸)으로 나눠 한 종목이 한 칸을 넘지 못함
  • 정해진 일정 — "공시 다음 날 진입, 며칠 뒤 청산"처럼 날짜가 규칙으로 고정, 감으로 연장하지 않음
  • 손절 규칙 — 진입 근거가 깨지는 지점이 진입 시점에 정해져 있고 자동 실행
  • 유휴 자금 관리 — 대기 현금은 안전한 지수 ETF에 보관, 매수 신호 시 즉시 회수
  • 모의 우선 — 새 전략은 모의 계좌에서 실제 시장가로 검증 후에만 실전 전환 검토. 백테스트는 상한선이라는 전제
  • 배포 시간 제한 — 시스템 업데이트는 매매가 몰리는 시간대를 피해 반영

7단계기록과 평가

기록 항목내용
판단 근거어떤 신호였는지, 각 에이전트가 뭐라고 판단했는지(반려 사유 포함)
체결 내역주문가 대비 실제 체결가(슬리피지 실측), 수수료·세금
청산 내역어떤 규칙으로 나왔는지(손절/기한/신호), 손익
당시 시장 상태재현·분석용 스냅샷
  • 수익률과 함께 승률, 최대 낙폭, 위험 대비 수익, 수중 기간(전고점 회복에 걸린 시간)을 봅니다.
  • 모의·실전 실측을 백테스트 기대치와 비교해 괴리가 크면 원인을 찾습니다.
  • 기준 미달 전략은 폐기하고 사유를 문서로 남깁니다.

예시매매 한 건의 생애주기

가상의 회사 "A사"로 실제 흐름을 재구성한 예입니다.

D일 16:40 — 공시 수집기가 A사의 "자기주식 취득 결정" 공시를 발견. 처리 단계가 원문에서 금액(예: 시가총액 대비 2%)과 방식을 추출.
D일 16:41 — 신호 단계: 전략 조건 대조. A사 주가가 52주 범위 바닥권인지 확인 → 부합, 후보 등록.
D일 16:42 — 에이전트 판단: 이벤트 분석 "과거 같은 유형 수백 건의 평균 초과수익 양수, 규모도 형식적 수준 아님". 가격·수급 "바닥권 충족". 시장 상태 "정상". 리스크 "슬롯 여유, 업종 쏠림 없음". 최종 관문: 승인 — 수량 슬롯 1칸, 진입 D+1 시초, 청산 D+7 종가, 중도 손절선 지정.
D+1일 09:00 — 잔고·한도 검증 통과 → API 매수 주문 → 체결 확인 → 기록 저장. 유휴 현금용 ETF에서 해당 금액 자동 회수.
D+2 ~ D+6 — 보유 감시: 매일 손절선·시장 상태 점검.
D+7일 15:20 — 규칙에 따라 자동 매도, 손익 기록. 이 1건이 전략 통계에 추가되어 다음 평가에 반영.

사람의 역할

  • 전략 승인 — 검증 통과 전략의 운용 여부 최종 결정
  • 실전 전환 결정 — 모의 성적을 보고 실전 투입 여부·금액 결정
  • 감독 — 검증 기준 준수와 기록의 온전함 감시
  • 개별 주문 불개입 — 사람이 감으로 개입하면 기록·평가가 무의미해지므로 개입하지 않는 것이 원칙

한계와 원칙

  • 백테스트 성과는 상한선입니다. 실전은 대체로 그보다 나쁘고, 시스템은 이를 전제로 설계돼 있습니다.
  • 수익을 보장하는 전략은 없습니다. 시스템이 하는 것은 "검증된 확률 우위를, 감정 개입 없이, 위험 한도 안에서 반복 실행"입니다.
  • 미래 예측이 아니라, 특정 사건 뒤에 통계적으로 반복되어 온 경향이 발생했을 때만 기계적으로 참여합니다.
  • 안 되는 것을 안 된다고 확정하는 것도 시스템의 산출물입니다.
이 탭의 목적 — 위 프로세스와 같은 시스템을 본인의 계좌·본인의 코드로 처음부터 직접 만들 수 있게, 필요한 이론·논리·수식·의사코드를 전부 적었습니다. 특정 회사의 코드를 베끼는 것이 아니라 방법을 배우는 문서입니다. 이 문서를 AI 코딩 도구(예: Claude)에 주고 "이대로 만들어줘"라고 해도 동작하는 뼈대가 나오도록 썼습니다.

G1준비물

  • 증권사 OpenAPI — 본인이 쓰는 증권사의 개발자 포털에서 API 사용 신청. 필요한 권한은 세 가지: 시세 조회(일봉·분봉), 계좌 조회(잔고·체결), 주문. 대부분 "모의투자" 전용 키를 따로 발급해 주므로 반드시 모의 키부터 발급.
  • 공시 OpenAPI — 금융감독원 전자공시(DART)가 무료 API를 제공. 회사별·기간별 공시 목록과 보고서 원문 데이터를 받을 수 있음.
  • LLM API 키 — AI 판단 계층에 사용. 여러 모델을 쓸 수 있는 중계 서비스가 편함.
  • 실행 환경 — 일반 PC면 충분. 서버 상시 가동이 필요한 건 실시간 매매 단계부터이고, 연구·백테스트는 로컬에서 다 됨. 언어는 무엇이든 되지만 데이터 처리 루프가 많으므로 배열 연산이 빠른 언어/방식 권장.
  • 비용 감각 — 수수료·세금은 증권사/국가 공시값을 쓰고, 슬리피지는 보수적으로 가정(뒤 G6). "낙관적 비용"이 최대의 적.

G2전체 아키텍처와 모듈 분리

다섯 모듈로 나눕니다. 나누는 이유는 각각 실패 방식이 달라서입니다 — 수집은 "빠짐"이 실패, 백테스트는 "미래 유출"이 실패, 실행은 "중복 주문"이 실패. 섞어 두면 어느 실패인지 알 수 없게 됩니다.

[수집기]  ──원본 저장──▶  [저장소]  ──읽기──▶  [백테스터/연구]
                              │                     │ (승인된 전략 규칙)
                              ▼                     ▼
                         [판단 계층(에이전트)] ──주문서──▶ [실행기] ──▶ 증권사 API
                              ▲                                │
                              └────────── [기록/평가] ◀────────┘
  • 수집기 — 외부 API에서 데이터를 받아 원본 그대로 저장. 판단 없음.
  • 저장소 — 파일 또는 DB. 원본과 가공본을 구분해 보관.
  • 백테스터/연구 — 과거 데이터로 전략을 실험·검증. 실행기와 완전히 분리.
  • 판단 계층 — 실시간 후보에 대해 규칙 + AI 에이전트로 승인/반려 결정.
  • 실행기 — 주문 전송과 포지션 관리만 담당. 여기에 전략 로직을 넣지 않음.
중요 원칙: 백테스터와 실행기는 같은 "체결 모델"과 같은 "전략 규칙 코드"를 공유해야 합니다. 백테스트 따로 실전 따로 구현하면 미묘한 차이(진입 시점 하루 차이 등)로 실전 성과가 검증과 무관해집니다.

G3데이터 저장 설계

시작은 "한 줄에 JSON 하나" 텍스트 파일(JSONL)로 충분합니다. 추가만 하는 구조라 손상에 강하고, 어떤 언어에서도 읽기 쉽습니다. 규모가 커지면 DB로 옮깁니다.

권장 스키마 (필드는 예시 — 핵심은 "무엇을 남기느냐")

// 봉(캔들) — 일봉이든 분봉이든 같은 구조
{"code":"종목코드","d":"20260115","t":"093000","o":시가,"h":고가,"l":저가,"c":종가,"v":거래량}

// 구조화된 공시 이벤트
{"date":"20260115","time":"1640","code":"종목코드","type":"자사주취득결정",
 "amount":금액,"method":"직접취득|신탁","ratio_mcap":시가총액대비비율,"raw_id":"원문식별자"}

// 매매 기록 (뒤 G11에서 확장)
{"ts":"...","code":"...","side":"buy","qty":수량,"order_px":주문가,"fill_px":체결가,
 "strategy":"전략이름","reason":"판단근거요약","exit_plan":{"stop":손절가,"until":"청산예정일"}}
  • 원본과 가공본 분리 — 공시 원문 응답은 원본대로 저장하고, 구조화(금액 추출 등)는 별도 파일로. 추출 로직을 고치면 원본에서 다시 만들 수 있어야 함.
  • 죽은 종목 포함 — 상장폐지 종목의 과거 데이터도 지우지 않음(생존 편향 방지).
  • 시각은 항상 문자열로 정렬 가능한 형식 — YYYYMMDD+HHMMSS로 통일하면 문자열 비교=시간 비교가 되어 버그가 줄어듦.

G4수집기 구현 논리

모든 수집기는 같은 뼈대를 가집니다:

대상목록 = 종목 × 기간(또는 페이지)
이미저장됨 = 저장소에서 마지막 저장 지점 로드          // 증분 수집
for 항목 in 대상목록:
    if 항목 in 이미저장됨: continue
    응답 = API호출(항목)                              // 실패 시 1~2회 재시도
    if 실패: 실패목록.추가(항목); continue             // 멈추지 말고 계속
    저장소.append(응답 그대로)
    sleep(호출간격)                                   // 속도 제한 준수
진행상황을 주기적으로 로그 (몇/전체, 실패 수, 예상 잔여시간)
  • 호출 간격 — 제공자의 초당 한도보다 여유 있게 (예: 한도의 절반). 한도 초과로 차단되면 훨씬 손해.
  • 체크포인트 — 중간에 꺼져도 이어서 받을 수 있게, "무엇까지 받았는지"를 파일 자체(마지막 줄)로 판단하거나 별도 기록.
  • 완결성 검사 — 수집 후 "종목별 일수 분포"를 찍어 구멍을 찾음. 예: 어떤 종목만 일수가 절반이면 원인(거래정지? 수집 실패?)을 확인.
  • 분봉처럼 큰 데이터 — 한 번에 안 주는 API가 많으므로 "하루를 몇 개 시간창으로 쪼개 여러 번" 요청하는 구조로. 총 소요시간 = 종목수 × 일수 × 호출수 × 간격으로 미리 계산해 계획.

G5지표 계산 수식

전부 "시점 t까지의 데이터만" 사용해야 합니다. 특히 표준편차·평균에 현재 봉을 포함하면 안 되는 경우(신호 판정에 쓸 때)를 주의하세요 — 급락 봉 자체가 평균을 끌어내려 신호를 왜곡합니다.

이동평균 SMA_n(t) = ( P(t) + P(t-1) + … + P(t-n+1) ) / n
수익률 r(t) = P(t) / P(t-1) − 1   ·   k분 수익률 r_k(t) = P(t) / P(t−k) − 1
변동성 σ(t) = 과거 N개 r의 표준편차 (현재 봉 제외, 롤링 창) — "이 종목의 평소 움직임 크기"
거래량 배율 vr(t) = V(t) / 평균(V(t−1) … V(t−30)) — "평소 대비 몇 배 터졌나"
VWAP(t) = Σ(P·V) / Σ(V) (당일 누적) — "오늘 산 사람들의 평단"
52주 위치 pos52(t) = ( P(t) − 52주최저 ) / ( 52주최고 − 52주최저 ) — 0이면 바닥, 1이면 천장
최대낙폭 MDD = min( 자산곡선(t) / 그때까지의최고점 − 1 )

롤링 표준편차는 매번 다시 합산하면 느리므로, 합과 제곱합을 유지하며 창에서 나가는 값을 빼고 들어오는 값을 더하는 방식(러닝 섬)으로 구현하면 수천만 봉도 몇 초에 처리됩니다.

G6백테스트 엔진

체결 모델 — 가장 중요한 부분

  • 진입은 "다음 봉 시가" — 신호를 본 봉의 가격으로는 살 수 없습니다(그 봉이 끝나야 신호를 알 수 있으므로). 판단은 봉 t에서, 체결은 봉 t+1의 시가로.
  • 손절은 비관적으로 — 봉 t의 저가가 손절선 아래면 체결가는 min(손절가, 봉 시가). 갭 하락으로 손절선보다 낮게 시작했다면 그 낮은 가격에 팔린 것으로 계산해야 합니다. 반대로 익절 목표 도달은 낙관하지 말 것.
  • 같은 봉에서 손절과 익절이 둘 다 가능하면 손절이 먼저 일어난 것으로 처리 (보수적 가정).

비용 모델

매수 실효단가 = 가격 × (1 + 슬리피지) × (1 + 수수료)
매도 실효수취 = 가격 × (1 − 슬리피지) × (1 − 수수료 − 거래세)
순수익률 = 매도 실효수취 / 매수 실효단가 − 1

슬리피지(주문가와 체결가의 차이)는 유동성에 따라 다르지만, 검증 단계에서는 편도 0.1~0.3%를 보수적으로 가정하고, 모의·실전에서 실측해 갱신합니다. 슬리피지를 0으로 두면 초단타류는 전부 흑자처럼 보입니다 — 실전에서 그대로 사라지는 이익입니다.

엔진 뼈대 (이벤트 드리븐)

이벤트목록 = 모든 신호 발생 시점을 시간순 정렬
포지션 = 없음
for 이벤트 in 이벤트목록:
    if 포지션 보유 중이고 규칙상 중복 진입 금지: continue
    if 진입조건(이벤트, 그 시점까지의 데이터만):
        진입가 = 다음 봉 시가 × 비용반영
        청산계획 = {손절가, 목표가(선택), 보유기한}
    for 봉 in 진입 이후의 봉들:
        if 저가 ≤ 손절가: 청산(비관 체결); break
        if 보유기한 도달 or 청산신호: 청산(종가); break
    기록.append({진입, 청산, 순수익률, 근거})
전 종목·전 기간을 도는 루프는 수천만 봉이어도 단순 산술이면 초 단위에 끝납니다. 느리다면 봉마다 객체를 만들거나 매번 배열을 다시 계산하는 구조가 원인입니다 — 종목별로 숫자 배열(가격·거래량·지표)을 한 번 만들어 놓고 인덱스로만 도세요.

G7검증 방법론 (수식·절차)

백테스트 수익이 나왔다고 끝이 아닙니다. 그 수익이 우연인지를 죽이는 절차가 본체입니다.

1) 통계적 유의성

t = 평균수익률 / ( 표준편차 / √건수 )

|t| ≥ 2면 "우연이라 보기 어렵다"의 최소선. 단, 실험을 많이 했다면(아래 4) 이 기준을 올려야 합니다.

2) 기간 분리

데이터를 앞/뒤 절반으로 나눠 각각 통계를 냅니다. 양쪽 다 양수여야 통과. 한쪽만 좋으면 "그 시기 전용"입니다. 가능하면 "앞 기간으로 규칙을 정하고 뒤 기간은 한 번만 본다"(아웃오브샘플)를 지키세요 — 뒤 기간을 여러 번 보며 규칙을 고치면 그것도 오염입니다.

3) 부트스트랩 (재추출)

for i in 1..1000:
    표본 = 매매기록에서 중복 허용 무작위 재추출 (연속성 보존을 위해 "날짜 블록" 단위 권장)
    수익률_i = 표본의 총수익 계산
양수비율 = 수익률_i > 0 인 비율   // 예: 95% 이상이면 견고

날짜 블록 단위로 뽑는 이유: 같은 날의 매매들은 서로 독립이 아니기 때문입니다(시장이 같이 움직임).

4) 무작위 대조군

전략과 같은 순간·같은 횟수로 무작위 선택을 시켰을 때의 분포를 만들고, 전략 성과가 그 분포의 상위 몇 %인지 봅니다. "그 시장·그 타이밍이면 아무거나 사도 벌었던 것"을 걸러냅니다.

5) 다중 실험 보정

파라미터 조합 K개를 실험하면 최고 성적은 K가 클수록 우연히도 좋아집니다. 대응: ① 실험 전에 가설과 판정 기준을 먼저 적는다(사전 등록) ② 최고 조합이 아니라 "이웃 조합들도 다 좋은지"(고원인지 뾰족한 봉우리인지)를 본다 ③ 기준 t를 올린다.

6) 미래 유출 체크리스트

  • 공시·뉴스의 발표 시각이 장중인지 마감 후인지 확인했는가 (마감 후면 다음 날 진입)
  • "그 날의 최대/최소/합계" 같은 당일 통계를 장중 판단에 쓰지 않았는가
  • 여러 신호의 "조합 완성"을 확인한 시점 이후에만 진입했는가
  • 체결을 낙관(신호 봉 가격, 목표가 우선 체결)하지 않았는가
  • 상장폐지 종목을 데이터에서 빼지 않았는가
  • 성과 좋은 종목/월을 사후에 골라 규칙에 넣지 않았는가

G8전략 설계 이론 — 어디서 엣지를 찾을 것인가

  • 이벤트 기반이 유리한 이유 — "언제 정보가 생겼는지"가 명확해서 인과 검증이 쉽고, 대조군(비슷하지만 이벤트가 없던 종목)을 만들 수 있습니다. 가격 모양만 보는 전략은 대조군을 만들기 어렵습니다.
  • 대조군 사고방식 — "이벤트 후 +2% 올랐다"만으로는 부족합니다. 같은 기간 비슷한 종목들이 +2% 올랐다면 이벤트의 효과는 0입니다. 항상 이벤트 있음 − 이벤트 없음의 차이를 재세요.
  • 엣지의 원천을 말로 설명할 수 있어야 함 — 왜 이 이득이 존재하고, 왜 아직 사라지지 않았는가? (예: "회사가 자기 주식을 사겠다는 커밋은 실제 매수 수요를 만든다", "공포 구간의 투매는 과잉반응이다") 설명이 안 되는 패턴은 데이터 마이닝일 확률이 높습니다.
  • 보유 기간과 비용의 산수 — 왕복 비용이 0.4%라면, 하루 10번 도는 전략은 매일 4%의 비용 허들을 넘어야 합니다. 보유가 짧을수록 필요한 예측력이 기하급수로 커집니다. 초단타가 어려운 것은 근성 문제가 아니라 산수입니다.
  • 포트폴리오 관점 — 전략 하나의 수익률보다, 서로 다른 시장 국면에서 작동하는 전략들의 조합(예: 추세장에 강한 자산배분 + 횡보장에 강한 이벤트 전략)이 최대 낙폭을 줄입니다.

G9AI 에이전트 계층 설계

설계 원칙

  • 계산은 코드가, 판단은 AI가 — 통계·지표·비용은 코드로 계산해서 AI에게 "재료"로 줍니다. AI에게 계산을 시키면 안 됩니다(느리고 틀림).
  • 역할 분리 — 하나의 만능 프롬프트보다, 관점이 다른 여러 에이전트(이벤트 해석 / 가격·수급 / 시장 상태 / 리스크)가 각자 짧게 판단하고 최종 판정자가 종합하는 구조가 편향에 강합니다.
  • 출력 형식 고정 — "결정: 매수|관망 / 확신: 0~10 / 이유: 1문장"처럼 형식을 강제하고, 파싱은 정규식으로. 자유 서술은 집계가 안 됩니다.
  • 기저율 제공 — "이런 상황은 과거 N번 있었고 평균 결과는 X%였다"를 반드시 프롬프트에 포함. 이걸 안 주면 AI는 근거 없이 낙관/비관합니다.
  • 캐싱 — 같은 입력의 호출 결과는 파일에 저장해 재사용. 검증을 여러 번 돌려도 비용이 한 번만 들고, 결과가 재현됩니다.
  • 합의 규칙 — M명 중 N명 이상 동의 + 거부권(시장 급락 등 특정 조건이면 무조건 반려). 수치는 백테스트로 정합니다.

프롬프트 골격 (예)

[역할] 너는 (관점)을 전문으로 하는 트레이더다.
[상황] 종목/시각/현재가/당일 흐름/최근 봉들/시장 상태  // 코드가 만들어 넣음
[과거 통계] 이런 유형의 상황은 과거 N회, 평균 결과 X%, 승률 Y%  // 기저율
[질문] 이 순간 진입할지 판단하라.
[형식] 결정: 매수|관망 / 확신: 0~10 / 이유: 1문장

AI 기여도의 검증 — 반드시 할 것

AI가 "고른 것"과 "고르지 않은 것"의 실제 성과를 같은 조건(같은 청산 규칙)으로 비교합니다. 차이가 0이면 AI는 그 역할에서 기여가 없는 것이고, 빼야 합니다. AI가 그럴듯한 이유를 말한다는 것과 실제로 잘 고른다는 것은 별개이며, 이건 측정으로만 알 수 있습니다.

G10실행기 (페이퍼 → 실전)

페이퍼(모의) 엔진 먼저

실전 주문 코드를 만들기 전에, "실시간 시세를 받아 가상으로 체결시키는" 페이퍼 엔진을 만듭니다. 체결 규칙은 백테스터와 동일하게 — 시장가 주문은 현재가 × (1+슬리피지)로 체결된 것으로 처리. 페이퍼로 몇 주 돌리면 백테스트와 실측의 괴리(비용, 타이밍)를 공짜로 배웁니다.

주문 상태기계

주문서(승인됨) → 사전검증(잔고/한도/중복/개장) → 전송 → 체결확인
   ├─ 전량 체결: 기록 + 청산계획 등록
   ├─ 부분 체결: 잔량 처리 규칙 적용 (재주문 or 취소)
   └─ 미체결 시간 초과: 취소 후 상황 재평가
  • 멱등성(중복 방지) — 주문마다 고유 ID를 만들고, 같은 ID로는 절대 두 번 전송되지 않게. 네트워크 오류로 "전송됐는지 모르는" 상태가 되면, 재전송 전에 반드시 체결 내역을 조회해 확인.
  • 상태의 원천은 증권사 — 내 프로그램이 기억하는 잔고와 실제 잔고가 다를 수 있습니다. 주기적으로 실제 계좌를 조회해 맞추되, 자동으로 "보정"한다며 금액을 덮어쓰는 로직은 만들지 마세요. 불일치는 사람에게 알리고 멈추는 게 안전합니다.
  • 안전장치는 판단과 분리 — 슬롯 한도, 일일 최대 주문 수, 최대 손실 한도(서킷브레이커)는 실행기 레벨에서 하드코딩. 판단 계층이 아무리 "사자"고 해도 실행기가 거부할 수 있어야 합니다.
  • 실전 전환 체크리스트 — ① 페이퍼 실측이 백테스트 기대의 하한선 안에 있는가 ② 모든 실패 경로(미체결·부분체결·API 다운)를 테스트했는가 ③ 소액부터 시작하는가 ④ 긴급 정지 방법이 있는가.

G11기록·평가 구현

기록 스키마 (한 매매 = 한 줄)

{"id":"고유ID","strategy":"전략명","code":"종목","side":"buy",
 "signal_ts":"신호시각","order_ts":"주문시각","fill_ts":"체결시각",
 "order_px":주문가,"fill_px":체결가,"qty":수량,
 "agents":{"이벤트":"승인:...","리스크":"승인:...","관문":"승인"},   // 반려면 반려 사유가 남음
 "exit":{"ts":"청산시각","px":가격,"why":"stop|expiry|signal","net":순수익률},
 "market_snapshot":{"지수등락":...,"하락종목비율":...}}

평가 지표 정의

  • 건당 평균 순수익률과 t값 — 전략의 심장박동. 매주 갱신.
  • 승률과 손익비 — 승률 40%여도 이길 때 크게 이기면 흑자일 수 있음. 둘을 같이 봐야 함.
  • MDD(최대낙폭) — 자산곡선 고점 대비 최대 하락. "견딜 수 있는 크기"인지가 실전 지속의 관건.
  • 수중 기간 — 전고점 회복까지 걸린 최장 시간. 2년 물릴 수 있는 전략을 견딜 수 있는가?
  • 슬리피지 실측 — 주문가 대비 체결가 차이의 분포. 백테스트 가정보다 나쁘면 가정을 갱신하고 전략을 재평가.

폐기 규칙을 미리 적어두기

"실측 N건 이상에서 건당 평균이 백테스트 하한선 밑이면 중단" 같은 폐기 조건을 운용 시작 전에 문서로 정합니다. 잃는 중에 정하면 사람은 반드시 "조금만 더"를 선택합니다.

G12구현 순서 로드맵

단계만드는 것완료 기준
1일봉 수집기 + 저장소수백 종목 × 수년치가 구멍 없이 저장되고, 재실행 시 증분만 받음
2지표 계산 + 백테스트 엔진단순 전략(예: 이동평균 교차)을 비용 포함으로 돌려 숫자가 나옴
3검증 배터리기간 분리·부트스트랩·무작위 대조가 버튼 하나로 돌아감
4이벤트 수집(공시) + 이벤트 전략 연구공시 구조화 데이터로 대조군 대비 초과수익을 잴 수 있음
5페이퍼 실행기실시간 시세로 가상 매매가 돌고, 기록이 스키마대로 쌓임
6AI 에이전트 계층판단이 기록되고, "AI 있음 vs 없음"의 성과 비교가 가능
7실전 전환 (소액)G10 체크리스트 전부 통과 + 슬리피지 실측 수집 시작

각 단계는 앞 단계가 완료 기준을 통과해야 넘어갑니다. 특히 3(검증)을 건너뛰고 5~7로 가는 것이 개인 자동매매의 가장 흔한 실패 경로입니다.

G13흔한 함정 체크리스트

  • 슬리피지 0 가정 → 초단타가 흑자처럼 보임 (실전에서 증발)
  • 상장폐지 종목 제외 → 과거 수익률 과대평가 (생존 편향)
  • 마감 후 공시를 당일 가격으로 진입 → 미래 정보 유출
  • 파라미터 수백 개 실험 후 최고만 채택 → 다중 검정 함정, 이웃 조합 확인 필수
  • 백테스트와 실행기의 규칙 코드가 따로 존재 → 검증과 실전이 무관해짐
  • AI의 그럴듯한 설명을 성과 측정 없이 신뢰 → 반드시 "고른 것 vs 안 고른 것" 비교
  • 자동 "정합성 보정"으로 계좌 데이터 덮어쓰기 → 불일치는 멈추고 사람에게 보고
  • 잃는 중에 폐기 기준을 정하기 → 운용 전에 미리 문서화
  • 검증 없이 실전 직행 → 로드맵 3단계는 건너뛸 수 없음

본 문서는 시스템의 동작 방식과 구축 방법을 설명하기 위한 것으로, 특정 종목·전략의 추천이나 수익 보장을 의미하지 않습니다.
