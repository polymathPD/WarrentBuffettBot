1. 프로젝트 개요

WarrenBuffett Bot은 개인 투자자(개미) 과열 신호를 역이용하는 역발상(Contrarian) 자동매매 시스템입니다. 매일 16:10 KST에 pykrx(일봉)와 KIS OpenAPI(투자자별 수급·신용잔고)로 당일 데이터를 수집하고, Claude API 기반 4개 에이전트 합의 게이트를 통과한 종목만 매수합니다. Railway PostgreSQL에 모든 상태를 저장하며 FastAPI 웹 대시보드로 포지션·거래내역을 관리합니다.

최대 포지션 수

12
SLOTS — DB 설정으로 런타임 변경 가능

진입 Heat 임계값

< 7.0
HEAT_AVOID — 낮을수록 보수적 진입

청산 Heat 임계값

≥ 8.5
HEAT_SELL — 과열 구간 도달 시 청산

최대 보유 기간

20일
MAX_HOLD_DAYS

손절 기준

-7%
STOP_PCT

AI 모델

Sonnet 4.6
에이전트당 최대 256 토큰 응답
핵심 혁신 4개 에이전트 합의 게이트: market_state·risk는 거부권(veto)을 보유하고, retail_flow·credit_heat는 2/2 합의 투표를 담당합니다. 어느 한 veto 에이전트가 "관망" 또는 "청산"을 리턴하면 즉시 매수 거부됩니다.

3. 일일 실행 흐름

APScheduler가 평일 16:10 KST에 daily_job()을 트리거합니다.

1
collect_daily() — pykrx → stock_daily 테이블 증분 upsert
2
collect_flow() — KIS OpenAPI 종목별 투자자매매동향 → investor_flow
3
collect_kis() — KIS OpenAPI 신용잔고 일별추이 수집 → credit_balance
4
compute_for_date() — 전 종목 heat_score 계산 → contrarian_signals
5
get_exit_candidates() → sell() — stop / expiry / heat_signal 해당 포지션 청산
6
_entry_signal_date() → get_entry_candidates() → gate.decide() → buy()
직전 거래일 신호에서 heat < 7.0 & 52주 하위 30% 종목을 필터 → 4에이전트 합의 통과 시 당일 시가로 모의 매수
7
summary() — 거래 통계 로그 출력
진입 신호일과 체결일이 다른 이유 체결 규칙은 "신호일 다음 거래일 시가"입니다(backtester/engine.py와 동일). 스케줄러는 장 마감 후 16:10에 도는데, 이 시점에 오늘 신호를 체결하려면 아직 존재하지 않는 내일 시가가 필요합니다. 그래서 6단계는 직전 거래일 신호를 대상으로 삼아 오늘 시가로 체결합니다. scheduler._entry_signal_date()가 이 날짜를 고르며, 신호 계산이 밀려 체결일이 오늘이 아니면(=지나간 날 시가로 체결하게 되면) 매수 단계를 건너뜁니다.

에이전트 게이트 내부 흐름

gate.decide(code, date)
  │
  ├─ market_state.analyze()  → decision: 매수 | 관망 | 청산
  │     ↳ fall_pct ≥ 70% 이면 하드코딩 "청산" (VETO)
  │
  ├─ risk.analyze()          → decision: 매수 | 관망
  │     ↳ free_slots = 0    → 하드코딩 "관망" (VETO)
  │     ↳ same_sector ≥ 3  → 하드코딩 "관망" (VETO)
  │
  ├─ retail_flow.analyze()   → decision: 매수 | 관망  (vote)
  │
  └─ credit_heat.analyze()   → decision: 매수 | 관망  (vote)

결과:
  veto 에이전트 중 하나라도 관망/청산 → approved = False
  retail_flow + credit_heat 중 "매수" < 2 → approved = False
  모두 통과 → approved = True → paper.buy() 호출

7. Collector 모듈 collector/

universe.py — 수집 대상 선정

target_codes(source)가 investor_flow·credit_balance 두 수집기의 대상 종목을 정합니다. FinanceDataReader.StockListing('KRX')의 Marcap을 읽어 시가총액이 MIN_MARCAP(3,000억) 이상인 종목만 남깁니다. KRX 조회라 KIS 요청 한도와 무관합니다.

대상 = (시총 3,000억 이상 ∪ 해당 source로 이미 수집된 종목) ∩ stock_daily 보유 종목
시총 하위 종목을 제외하는 이유 비용 모델이 편도 슬리피지 0.2%(SLIP_BPS=20)를 가정하는데, 거래대금이 얇은 종목에서는 성립하지 않습니다. 게다가 역발상 진입 필터(heat 낮음 + 52주 하위 30%)는 소외되고 하락한 종목을 고르는 필터라 비유동 소형주를 구조적으로 후보 상위에 올립니다. 단순 노이즈가 아니라 체계적 편향이므로 수집 단계에서 잘라냅니다.
이미 수집한 종목은 시총과 무관하게 유지합니다 FDR이 주는 시총은 현재 값입니다. 과거에는 대형주였거나 이후 상장폐지된 종목을 소급 제외하면 시계열에 구멍이 생기고 백테스트에 생존 편향이 들어갑니다. 하필 역발상 전략은 '얻어맞은 종목'을 사므로, 실제로 상장폐지까지 간 종목만 빠지면 결과가 실제보다 좋게 나옵니다. 그래서 collect_cursor에 이미 기록이 있는 종목은 유니버스에 계속 포함시킵니다 (증분 수집이라 비용은 종목당 하루 1페이지 수준).

collect_kis(start_date, end_date)도 동일한 증분 수집 구조이며, KIS API 키 미설정 시 collect_stub()(0 채움)으로 자동 폴백합니다. 결제일자 기준이라 최신 데이터가 영업일 대비 며칠 뒤처집니다.

공통 구조: 역방향 페이지네이션과 커서 기록 규칙 두 수집기는 같은 구조를 씁니다. 한 번의 호출이 최대 30건만 반환하므로 anchor_date를 과거로 당겨가며 start_bound에 도달할 때까지 반복 조회하고, 페이지마다 ON CONFLICT DO NOTHING으로 삽입합니다. 다음 페이지가 앵커 날짜를 다시 포함하므로 실효 진행은 페이지당 약 29거래일입니다. 응답의 최과거일이 현재 앵커보다 과거로 밀리지 않으면 더 줄 데이터가 없다고 보고 종료합니다 — 이 가드가 없으면 같은 요청을 한도까지 반복하게 됩니다.

collect_cursor는 수집을 완주했을 때만 기록합니다. 완주란 (a) start_bound까지 훑었거나 (b) API가 더 줄 데이터가 없는 경우(신규상장·상장폐지)입니다. MAX_PAGES_PER_CODE(120) 한도를 소진해 끝난 경우에는 커서를 남기지 않고 오류 목록에 기록해 다음 실행에서 다시 시도합니다. 이때 커서를 남기면 다음 실행의 start_bound가 그 날짜로 올라가, 받지 못한 과거 구간이 영구히 결손되기 때문입니다.

종목 단위로 try/except를 감싸므로 한 종목의 네트워크·DB 실패가 전체 스윕을 중단시키지 않습니다. 실패한 종목에는 커서가 남지 않아 다음 실행에서 자동으로 재시도됩니다.

8. Processor 모듈 processor/

signals.py — Heat Score 계산

대상 날짜의 전 종목에 대해 30일 이동 기준(window) 대비 오늘 값의 비율을 계산하고, 3가지 요소를 결합하여 0~10 스케일의 heat_score를 산출합니다.

구성 요소 및 가중치

요소계산식최대 기여
개인 순매수 비율(individual_flow_ratio - 1.0) × 3.04.0점
신용 급등 비율(credit_surge_ratio - 1.0) × 3.03.0점
거래량 급등 비율(volume_ratio - 1.5) × 2.03.0점

Signal 분류

heat_score < 7.0   → "neutral"  (진입 가능)
7.0 ≤ score < 8.5  → "avoid"   (진입 불가)
score ≥ 8.5        → "sell"    (청산 신호)
결측 지표는 0점으로 취급됩니다 _heat()는 결측(NaN) 지표를 빼고 남은 항목의 원점수 합을 반환합니다. 정규화하지 않기 때문에 수급·신용 데이터가 없는 종목일수록 heat_score가 낮아지고, 3개 지표가 모두 없으면 0.0/"neutral"이 됩니다. 지표 개수가 다른 점수끼리는 비교가 성립하지 않으므로, get_entry_candidates()는 세 지표가 모두 존재하는 행만 후보로 삼습니다(9번 항목 참고).

numpy 계산 결과는 contrarian_signals에 넣기 전 파이썬 네이티브 float()로 캐스팅합니다 — np.float64를 그대로 psycopg2에 넘기면 INSERT가 실패합니다.

indicators.py — 기술적 지표

SMA, rolling_std, volume_ratio, 52주 위치(pos_52w), 일간 로그 수익률 등을 numpy 배열로 계산합니다. 현재 메인 파이프라인에서 직접 호출되지는 않고 전략 분석용으로 준비되어 있습니다. 모든 지표는 t-1 데이터만 참조하여 look-ahead bias를 방지합니다.

9. Strategy 모듈 strategy/contrarian.py

진입 후보 (get_entry_candidates)

다음 조건을 모두 충족하는 종목만 반환합니다:

  • heat_score < HEAT_AVOID (기본 7.0)
  • signal = 'neutral'
  • individual_flow_ratio, credit_surge_ratio, volume_ratio가 모두 NOT NULL
  • positions 테이블에 없는 종목 (미보유)
  • 52주 위치 ≤ 30% (52주 저점 근처)

출력: [{code, close, heat_score, pos52w}, ...] — heat_score 오름차순 정렬

세 지표를 모두 요구하는 이유 heat_score는 정규화되지 않은 원점수 합이라 지표가 결측일수록 값이 낮아집니다. 위 정렬이 heat_score 오름차순이므로, 이 조건이 없으면 데이터가 없는 종목이 "가장 안 과열된 종목"으로 둔갑해 후보 상위를 차지합니다. 지표 개수가 다른 점수끼리는 애초에 비교가 성립하지 않으므로 세 축이 모두 있는 종목만 후보로 삼습니다.

따라서 investor_flow 또는 credit_balance 수집이 비어 있으면 진입 후보가 나오지 않습니다. 이는 결측을 매수 신호로 오해하는 것보다 안전한 쪽으로 실패하도록 한 선택입니다.

11. Executor 모듈 executor/

paper.py — 모의 매매 운영 중

buy(code, name, signal_date, close_px, heat_score, agents_summary)

  1. positions 수 ≤ SLOTS 확인
  2. stock_daily에서 signal_date 다음 거래일 시가 조회 — 없으면 체결하지 않고 거부
  3. 매수 비용 모델 적용: entry_px = next_open × (1 + SLIP) × (1 + FEE)
  4. 손절가 계산: stop_px = entry_px × (1 - STOP_PCT)
  5. positions 삽입, trades 삽입 (side='buy')

signal_date에는 직전 거래일이 들어옵니다(scheduler._entry_signal_date()). 그래야 2단계가 조회하는 "다음 거래일"이 오늘이 되어 당일 시가로 체결됩니다. 오늘 날짜를 넘기면 아직 존재하지 않는 내일 봉을 찾게 되어 모든 매수가 거부됩니다.

sell(code, name, qty, entry_px, close_px, reason)

  1. 매도 비용 모델 적용: fill_px = close_px × (1 - SLIP) × (1 - FEE - TAX)
  2. 수익률 계산: realized_pct = fill_px / entry_px - 1
  3. 원 매수 trade에 exit_reason, realized_pct 업데이트
  4. 매도 trade 삽입, positions에서 삭제

13. Backtester 모듈 backtester/

engine.py — 이벤트 기반 백테스트

run(start, end, ...)는 contrarian_signals를 직접 조회하여 진입→청산 시뮬레이션을 수행합니다.

시뮬레이션 로직:
1. heat < heat_avoid & signal='neutral' 종목 → 다음 거래일 시가로 진입
2. 이후 20일간 매일 확인:
   a. low ≤ stop_px   → 손절 (비관적 fill: stop_px 사용)
   b. heat ≥ heat_sell → 과열 청산 (당일 종가)
   c. days_held ≥ max_hold → 만기 청산 (당일 종가)
3. 비용 모델(cost_model.py) 적용하여 순수익률 계산
중복 포지션 방지 active 딕셔너리가 종목별 마지막 청산일을 들고 있으며, 신호일이 그 청산일 이하이면 이미 보유 중인 것으로 보고 건너뜁니다. 같은 종목에 매일 신호가 떠도 포지션은 하나만 열리고, 청산 이후 신호부터 다시 진입할 수 있습니다.

cost_model.py

buy_price(px)  = px × (1 + SLIP) × (1 + FEE)
sell_price(px) = px × (1 - SLIP) × (1 - FEE - TAX)
net_return     = sell_price(exit) / buy_price(entry) - 1

validator.py — 아웃오브샘플 검증

검증 방법성공 기준
전체 기간 백테스트t-value ≥ 2.0
전반/후반 분할양 기간 모두 양의 평균 수익률
부트스트랩 (1000회)양의 평균 비율 ≥ 80%
무작위 대조군 (200회)전략 수익률이 상위 20% 이내

검증용 보조 스크립트 (프로젝트 루트)

17. 핵심 비즈니스 로직

Heat Score 공식

heat_score = clamp(
    (flow_ratio - 1.0) * 3.0      # 개인 과열 기여 [0, 4]
  + (credit_ratio - 1.0) * 3.0    # 신용 과열 기여 [0, 3]
  + (vol_ratio - 1.5) * 2.0,      # 거래량 급등 기여 [0, 3]
  0, 10
)

진입 조건 체크리스트

  1. heat_score < 7.0
  2. signal = 'neutral'
  3. heat_score의 3개 입력 지표가 모두 존재 (결측 종목 배제)
  4. 미보유 종목
  5. 52주 위치 ≤ 30%
  6. market_state 에이전트 → 매수 승인
  7. risk 에이전트 → 매수 승인
  8. retail_flow + credit_heat 모두 "매수" 투표

청산 조건 (우선순위)

  1. 손절: close ≤ entry × (1 - 0.07)
  2. 만기: held_days ≥ 20
  3. 과열 청산: heat_score ≥ 8.5

비용 모델

# 매수 실효가
entry_px = market_px × 1.0020 × 1.000150   # +0.215%

# 매도 실효가
exit_px  = market_px × 0.9980 × 0.999650   # -0.235%  (수수료 0.015% + 세금 0.20%)

# 순수익률
net_return = exit_px / entry_px - 1
Look-Ahead Bias 방지 모든 지표는 t-1 데이터 기준으로 계산됩니다. 진입은 신호 발생 다음 거래일 시가 기준으로 실행됩니다.

19. 미완성 항목 & 향후 개선

1. 과거 데이터 축적 및 백테스트 재검증 investor_flow·credit_balance 전 종목 백필이 끝나면 backfill_signals.py로 과거 contrarian_signals를 재계산하고 백테스트를 다시 검증해야 합니다 (검증용 보조 스크립트 참고).
2. 실전 주문 실행 연동 High Priority executor/live.py의 buy/sell을 scheduler 파이프라인에 연결해야 합니다. 주문 확인 및 부분 체결 처리 로직도 필요합니다.
3. DART 공시 데이터 필터링 주요 공시일 전후 종목을 진입 후보에서 제외하면 돌발 리스크를 줄일 수 있습니다.
4. 에이전트 고도화 Anthropic prompt caching 활용으로 반복 분석 비용 절감 가능. 도구 사용(tool use)으로 에이전트가 DB를 직접 조회하는 방식도 검토할 수 있습니다.
5. 대시보드 고도화 WebSocket 기반 실시간 P&L 스트리밍, 백테스트 결과 뷰어, 에이전트 의사결정 이유 표시.
